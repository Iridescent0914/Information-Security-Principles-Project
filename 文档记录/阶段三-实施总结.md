# 阶段三：完整 UDP 握手协议实施总结

## 1. 阶段目标

阶段三的目标是把阶段二已经独立验证过的协议格式和密码学组件真正组合起来，使：

```text
Kali Client
172.30.0.2
        │
        │ UDP 2026
        ▼
VMware Ubuntu Server
<SERVER_VPN_IP>
```

通过真实网络完成完整握手：

```text
ClientHello
    ↓
ServerHello
    ↓
ClientKeyExchange
    ↓
ServerKeyExchange
    ↓
ECDH
    ↓
Transcript Hash
    ↓
HKDF Session Key
    ↓
ClientFinished
    ↓
ServerFinished
    ↓
ESTABLISHED
```

本阶段最终完成了：

- 服务端自签名证书生成；
- ClientHello / ServerHello 二进制格式；
- ClientKeyExchange / ServerKeyExchange 二进制格式；
- ClientFinished / ServerFinished 二进制格式；
- Kali 与 VMware 的真实 UDP `2026` 握手；
- 客户端预置服务端证书检查；
- secp256r1 临时 ECDH；
- 双方 Pre-Master Secret 一致；
- 双方 Transcript Hash 一致；
- HKDF-SHA256 派生相同 16 字节 Session Key；
- ClientFinished 验证；
- ServerFinished 验证；
- 双方进入 `ESTABLISHED`；
- tcpdump 抓取完整 6 个握手报文；
- `.pcap` 文件保存；
- 自定义脚本解析 6 个握手 Subtype。

本阶段仍然**不接入 TUN、不配置 NAT、不传输真实 IP 数据包**。

# 3. 阶段三实现约定

为了保持实现复杂度与课程要求一致，本阶段采用以下简化设计。

## 3.1 外层协议

沿用阶段二：

```text
Magic Number      2 字节  "TJ"
Packet Type       1 字节
Sequence Number   4 字节
Payload Length    2 字节
Payload           变长
```

固定头：

```text
9 字节
```

握手阶段：

```text
Packet Type = 0x01
Sequence Number = 0
```

## 3.2 握手子类型

```text
0x01 = ClientHello
0x02 = ServerHello
0x03 = ClientKeyExchange
0x04 = ServerKeyExchange
0x05 = ClientFinished
0x06 = ServerFinished
```

## 3.3 密码套件

当前只支持一个套件：

```text
0x0001
```

其含义为当前课程实现中采用的：

```text
secp256r1 ECDH
HKDF-SHA256
AES-128-GCM
HMAC-SHA256 Finished
```

## 3.4 Session Key

使用 HKDF-SHA256 派生：

```text
16 字节 Session Key
```

当前简化方案中：

- Finished 使用该 Session Key；
- 后续 AES-128-GCM 数据加密也使用该 Session Key；
- 不额外拆分 Client/Server 方向密钥；
- 不额外派生独立 Finished Key。

# 4. 生成服务端自签名证书

在 VMware Ubuntu：

```bash
cd ~/secure_tunnel
mkdir -p certs
```

生成 secp256r1 私钥：

```bash
openssl ecparam \
  -name prime256v1 \
  -genkey \
  -noout \
  -out certs/server_key.pem
```

生成自签名证书：

```bash
openssl req \
  -new \
  -x509 \
  -sha256 \
  -key certs/server_key.pem \
  -out certs/server_cert.pem \
  -days 3650 \
  -subj "/CN=TJVPN-Server"
```

限制私钥权限：

```bash
chmod 600 certs/server_key.pem
```

检查：

```bash
openssl x509 \
  -in certs/server_cert.pem \
  -noout \
  -subject \
  -issuer \
  -dates
```

由于是自签名证书：

```text
Subject = Issuer
```

证书与私钥用途：

```text
server_cert.pem
→ 公开证书
→ VMware 与 Kali 均保存

server_key.pem
→ 服务端私钥
→ 只保存在 VMware
→ 不复制给 Kali
```

# 6. 客户端证书检查方式

当前最低实现不建立完整 CA 信任链。

客户端预置：

```text
certs/server_cert.pem
```

握手时：

1. ServerHello 携带服务端证书；
2. Kali 解析收到的 PEM 证书；
3. 转换为 DER；
4. Kali 将本地预置证书同样转换为 DER；
5. 比较两份 DER 字节；
6. 完全一致则认为服务端证书检查通过。

客户端成功日志：

```text
[CERT] Server certificate verified
```

当前实现没有额外加入：

- CA 链验证；
- 证书撤销；
- ECDH 参数签名；
- 完整 PKI。

这些属于本课程最低实现之外的增强项。

# 9. ClientKeyExchange / ServerKeyExchange

格式：

```text
Subtype             1 字节
Public Key Length   2 字节
Public Key          变长
```

secp256r1 使用 X9.62 非压缩点：

```text
0x04 || X(32B) || Y(32B)
```

公钥长度：

```text
65 字节
```

因此 KeyExchange Payload：

```text
1 + 2 + 65 = 68 字节
```

测试：

```text
Client ECDH public key length = 65
Server ECDH public key length = 65
```

---

# 10. ClientFinished / ServerFinished

格式：

```text
Subtype              1 字节
Verify Data Length    2 字节
Verify Data          32 字节
```

Verify Data：

```text
HMAC-SHA256(Session Key, Transcript Hash)
```

因此 Payload：

```text
1 + 2 + 32 = 35 字节
```

# 17. 完整 Handshake Transcript

```text

||

||

||
```

```text

IP 头

```

计算：

```text

```

# 18. 真实 HKDF Session Key

HKDF 输入：

```text
Pre-Master Secret
+
Client Random
+
Server Random
+
Transcript Hash
```

使用：

```text
HKDF-SHA256
```

输出：

```text
16 字节 Session Key
```

某次真实握手中，两端：

```text
Session Key SHA256 =
cb539183226541f7479affb2a51c7ad7646ec2c4df3dddeb4434090c03759055
```

完全一致。

因此已经证明：

```text
Client:
ECDH → Transcript → HKDF

Server:
ECDH → Transcript → HKDF

得到同一 Session Key
```

# 19. 加入 ClientFinished

```text

    Transcript Hash
```

发送：

```text

```

```text

```

```text
hmac.compare_digest()
```
