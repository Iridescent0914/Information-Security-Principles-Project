# 阶段五：接入 TUN、传输真实 IPv4 Packet 与内外层抓包验证实施总结

## 1. 阶段目标

阶段五的目标是在阶段四已经完成：

```text
完整握手
→ ESTABLISHED
→ AES-128-GCM DATA
→ 双向加密字符串
→ Sequence Number 抗重放
→ Ciphertext / Auth Tag 篡改检测
→ CLOSE
```

的基础上，把 DATA 的明文内容从固定测试字符串：

```text
b"hello secure tunnel"
```

替换为：

```text
从 tjvpn0 读取到的完整 IPv4 Packet
```

本阶段重点完成：

- 在 Kali 和 VMware Ubuntu 两端创建自定义 TUN 接口 `tjvpn0`；
- Kali `tjvpn0 = 10.8.0.2/24`；
- VMware `tjvpn0 = 10.8.0.1/24`；
- 两端 `tjvpn0` MTU 固定为 `1300`；
- 保持 VMware OpenConnect 课程 VPN 的 `tun0` 不变；
- 使用 `select.select()` 同时监听 TUN FD 和 UDP Socket；
- 从 TUN 读取真实 IPv4 Packet；
- 使用阶段四的 AES-128-GCM DATA 逻辑进行加密；
- 通过 UDP `2026` 在 Kali 与 VMware 之间传输；
- 对端解密后将原始 IPv4 Packet 写回 `tjvpn0`；
- 实现 `10.8.0.2 ↔ 10.8.0.1` 的 ICMP Ping；
- 通过 tcpdump 分别验证内层 ICMP 和外层加密 UDP；
- 验证 CLOSE 后两端 `tjvpn0` 自动销毁；
- 验证 Kali 原默认路由和 VMware OpenConnect `tun0` 均未被破坏。

阶段五不配置公网 NAT，也不修改 Kali 默认路由。

```text
12B IV
+
Ciphertext

```

```text
Client → Server：1, 2, 3, ...

```

接收端采用严格递增规则：

```text
sequence <= last_received_sequence
→ reject
```

并且只有 AES-GCM 认证成功后才推进：

```text
last_received_sequence
```

# 5. 创建 tun_utils.py

两端创建相同的：

```text
tun_utils.py
```

核心功能：

```text
打开 /dev/net/tun
↓
ioctl(TUNSETIFF)
↓
IFF_TUN | IFF_NO_PI
↓
创建 tjvpn0
```

固定：

```text
TUN_NAME = "tjvpn0"
```

其中：

```text
IFF_TUN
```

表示创建三层 TUN 设备，程序直接处理 IP Packet。

```text
IFF_NO_PI
```

表示 TUN 读写数据中不附带 Linux 额外的 4 字节 Packet Information Header。

因此：

```python
os.read(tun_fd, 65535)
```

得到的第一个字节就是 IP Header 的 Version/IHL 字段。

# 10. 阶段五事件循环

客户端和服务端都使用：

```python
select.select(
    [tun_fd, sock],
    [],
    [],
)
```

同时等待：

```text
tjvpn0
UDP Socket
```

数据方向一：

```text
TUN readable
    ↓
os.read(tun_fd)
    ↓
完整 IPv4 Packet
    ↓
encrypt_data()
    ↓
TJ DATA
    ↓
UDP sendto()
```

数据方向二：

```text
UDP readable
    ↓
recvfrom()
    ↓
decrypt_data()
    ↓
恢复 IPv4 Packet
    ↓
os.write(tun_fd, ip_packet)
```

# 11. IPv4 Packet 检查

程序从 TUN 读取后执行：

```text
ip_version = ip_packet[0] >> 4
```

如果：

```text
ip_version == 4
```

才进入自定义隧道。

如果：

```text
ip_version != 4
```

则丢弃。

运行过程中出现过：

```text
[DROP] Non-IPv4 packet from TUN version=6 len=48
```

这是 Linux 在 `tjvpn0` 上产生的 IPv6 link-local / 邻居相关流量。

本课程最低实现只处理 IPv4，因此：

```text
version=6
→ drop
```

是预期行为，不属于故障。

# 20. 外层 DATA 十六进制验证

读取：

```bash
sudo tcpdump -nn \
  -r ~/secure_tunnel/pcap/05_outer_udp.pcap \
  -X
```

第一个抓到的 DATA UDP Payload 开头可看到：

```text
54 4a 02 00 00 00 05 00 70 ...
```

解释：

```text
54 4a       → Magic = "TJ"
02          → Packet Type = DATA
00 00 00 05 → Sequence Number = 5
00 70       → Payload Length = 112
```

后续：

```text
12B IV
84B Ciphertext
16B Auth Tag
```

因此：

```text
Payload Length
= 12 + 84 + 16
= 112
= 0x0070
```

完整 UDP Payload：

```text
9 + 112
= 121 B
```

与 tcpdump：

```text
UDP, length 121
```

完全一致。
