# 阶段六：路由、IPv4 转发、NAT 与公网访问实施总结

## 1. 阶段目标

阶段六的目标是在阶段五已经实现：

```text
Kali tjvpn0 = 10.8.0.2/24
        ↕
自定义 AES-128-GCM UDP 2026 隧道
        ↕
VMware tjvpn0 = 10.8.0.1/24
```

的基础上，让 Kali 的真实业务流量继续经过 VMware Ubuntu 的 Linux 转发与 NAT 访问公网。

本阶段需要完成：

- VMware 确认公网出口；
- 开启 `net.ipv4.ip_forward`；
- 配置 `iptables` MASQUERADE；
- 配置双向 FORWARD；
- 先让课程指定目标 `202.120.2.101/32` 进入 `tjvpn0`；
- 验证 `ping 202.120.2.101`；
- 在切换默认路由前固定自定义 VPN Server 的 `/32` 物理路由；
- 保证自定义 VPN 外层 UDP `2026` 不发生隧道递归；
- 保证 SSH 管理路径继续经过 Kali `eth0`；
- 将 Kali 默认路由切换到 `tjvpn0`；
- 验证 `ping 1.1.1.1`；
- 验证 DNS；
- 验证 `curl`；
- 验证 `wget`；
- 验证 `apt update`；
- 在 VMware `ens33` 抓包验证 NAT 后源地址；
- 保存 NAT/FORWARD 计数器；
- 完成阶段六清理与网络状态恢复；
- 确认没有阶段六 iptables 残留。

阶段六完成后，Kali 已经可以把普通 IPv4 业务通过自定义安全隧道发送到 VMware，再由 VMware NAT 到公网。

# 9. 配置 MASQUERADE

VMware 添加：


```text

```


从而使公网返回流量能够回到 VMware，再反向进入自定义隧道。

# 10. 配置 FORWARD

允许：

```text
tjvpn0 → ens33
```

规则：

```bash
sudo iptables -A FORWARD \
  -i tjvpn0 \
  -o ens33 \
  -j ACCEPT
```

允许返回：

```text
ens33 → tjvpn0
```

规则：

```bash
sudo iptables -A FORWARD \
  -i ens33 \
  -o tjvpn0 \
  -m conntrack \
  --ctstate RELATED,ESTABLISHED \
  -j ACCEPT
```

配置完成后初始计数器为：

```text

0 bytes
```


```text

→ tjvpn0
→ VPN UDP
→ tjvpn0
→ ...
```

即隧道递归。

# 26. 为什么 apt update 要强制 IPv4

当前阶段五/六代码只处理：

```text
IPv4 Packet
```

程序读取 TUN 后：

```text
ip_version = ip_packet[0] >> 4
```

只有：

```text
version = 4
```

才进入隧道。

IPv6：

```text
version = 6
```

会输出：

```text
[DROP] Non-IPv4 packet from TUN version=6
```

因此为了让：

```text
curl
wget
apt
```

稳定使用当前已实现的数据平面，测试统一强制 IPv4。

这属于当前最低实现的已知限制，不属于阶段六故障。

# 30. 阶段六清理顺序

阶段六结束时严格按以下顺序清理：

```text
1. Kali 恢复 default → eth0
2. 删除专用公网目标路由
3. 删除 Server /32 保护路由
4. 正常 CLOSE 自定义 VPN
5. 两端 tjvpn0 自动删除
6. VMware 删除 NAT
7. VMware 删除 FORWARD
8. VMware 恢复 ip_forward
9. 保留老师 OpenConnect tun0
```

这样避免在 VPN 仍依赖路由时过早删除底层网络。
