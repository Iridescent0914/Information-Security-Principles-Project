# 阶段四：加密 DATA、抗重放、篡改检测与 CLOSE 实施总结

## 1. 阶段目标

阶段四的目标是在阶段三完整握手成功、双方已经进入：

```text
ESTABLISHED
```

之后，继续实现真正的数据阶段。

本阶段完成：

- `Packet Type = 0x02` 的 DATA 报文；
- 使用阶段三握手得到的同一把 16 字节 Session Key；
- AES-128-GCM 加密与解密；
- 每个 DATA 包包含：
  - 12 字节 IV；
  - Ciphertext；
  - 16 字节 Auth Tag；
- Client → Server 加密字符串传输；
- Server → Client 加密字符串返回；
- 每个方向独立维护 Sequence Number；
- 简单严格递增的抗重放检查；
- 重放报文拒绝；
- Ciphertext 篡改检测；
- Auth Tag 篡改检测；
- `Packet Type = 0x03` CLOSE；
- 完整阶段四 pcap 抓包；
- 验证抓包中不存在 DATA 明文。

本阶段仍然没有接入真实 TUN IP Packet。

也就是说，阶段四验证的是：

```text
完整握手
    ↓
ESTABLISHED
    ↓
AES-GCM DATA
    ↓
双向加密字符串
    ↓
重放与篡改检测
    ↓
CLOSE
```

下一阶段才把普通字符串替换成从 `tjvpn0` 读取的真实 IP Packet。

# 5. DATA 报文格式

外层继续使用阶段二定义的 9 字节 TJ 协议头：

```text
Magic Number      2 B
Packet Type       1 B
Sequence Number   4 B
Payload Length    2 B
```

DATA：

```text
Packet Type = 0x02
```

Payload：

```text
IV
+
Ciphertext
+
Auth Tag
```

具体：

```text
12B IV
+
N 字节 Ciphertext
+
16B Auth Tag
```

完整 DATA：

```text
TJ Header
+
12B IV
+
Ciphertext
+
16B Auth Tag
```

当前最低实现：

- 不使用 AAD；
- 每包使用 `os.urandom(12)` 生成新的 IV；
- Sequence Number 独立用于防重放；
- 不把 Sequence Number 拼入 IV。

# 6. DATA Sequence Number 规则

本阶段采用：

```text
Client → Server:
1, 2, 3, ...

Server → Client:
1, 2, 3, ...
```

两个方向分别维护自己的发送序号。

所以第一次正常双向 DATA 中：

```text
Client DATA Sequence Number = 1
Server DATA Sequence Number = 1
```

是正确的。

接收端维护：

```text
last_received_sequence
```

当前最低实现采用严格递增规则：

```text
if sequence <= last_received_sequence:
    reject
```

因此：

- 重复序号拒绝；
- 旧序号拒绝；
- 当前实现不支持 UDP 乱序。

# 7. AES-GCM 加密逻辑

`encrypt_data()` 流程：

```text
输入：
Session Key
Sequence Number
Plaintext
```

生成：

```text
12B IV
```

执行：

```text
AESGCM(session_key).encrypt(
    iv,
    plaintext,
    None
)
```

`cryptography` 返回：

```text
Ciphertext || 16B Auth Tag
```

拆分：

```text
Ciphertext = encrypted[:-16]
Auth Tag   = encrypted[-16:]
```

最终 Payload：

```text
IV || Ciphertext || Auth Tag
```

再封装：

```text
Packet Type = DATA = 0x02
Sequence Number = 当前方向发送序号
```

---

# 8. AES-GCM 解密逻辑

`decrypt_data()`：

1. 解析外层 TJ Header；
2. 确认：

```text
Packet Type = DATA
```

3. 检查 Sequence Number；
4. 如果：

```text
sequence <= last_received_sequence
```

立即抛出：

```text
ReplayError
```

5. 解析：

```text
IV
Ciphertext
Auth Tag
```

6. 调用：

```text
AESGCM.decrypt()
```

7. 如果 Auth Tag 校验失败：

```text
DataAuthenticationError
```

8. 只有 AES-GCM 认证成功后，调用方才更新：

```text
last_received_sequence
```

这个顺序很重要。

否则攻击者可以用认证失败的伪造包提前占用合法 Sequence Number。

# 16. 认证失败时不推进 Sequence Number

当前处理逻辑是：

```text
正常 seq=1
→ AES-GCM 成功
→ last_received_sequence = 1
```

重放：

```text
seq=1
→ ReplayError
→ last_received_sequence 保持 1
```

篡改 Ciphertext：

```text
seq=2
→ AES-GCM authentication failed
→ last_received_sequence 仍为 1
```

篡改 Tag：

```text
seq=3
→ AES-GCM authentication failed
→ last_received_sequence 仍为 1
```

这是正确的。

只有：

```text
序号合法
+
AES-GCM 认证成功
```

之后才能推进接收序号。
